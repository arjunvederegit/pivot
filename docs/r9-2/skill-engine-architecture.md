# R9.2 — Skill-engine architecture

How player intelligence is computed, stored, retrieved and kept honest. Companion documents:
[shooting-intelligence-methodology.md](shooting-intelligence-methodology.md) (the statistics),
[model-safety-and-promotion.md](model-safety-and-promotion.md) (what can and cannot be served).

## 1. One sentence

A **backend service** (`PlayerIntelligenceService`) returns typed `PlayerIntelligenceRecord`s that keep **what a player did
(measured)**, **what we can infer about his underlying ability (inferred)** and **what we can defensibly project (projected)** apart,
each with its sample, model version, data provenance, uncertainty and limitations — and *declines*, with a reason, anything it cannot
support. Nothing in it changes a live rating.

## 2. What was reused, what was added

R9.2 is built **on** R8 and R9.1, not beside them.

| Layer | Reused (unchanged unless stated) | Added by R9.2 |
| --- | --- | --- |
| Data foundation (R8) | canonical seasons (`canonical.seasons`), `player_season_stats` regular-season rows, provider provenance (`source_retrieved_at`), identity crosswalk and its confidence levels | — (no schema change; **no migration**) |
| Panel (R9.1) | `PlayerSeasonPanel` / `AsOfPanel` (a view that physically cannot contain a later season), unit validation, `replace_future` for the leakage audit | `player_intelligence.panel.build_skill_panel` = R9.1's panel + integer shot counts |
| Evaluation (R9.1) | rolling-origin backtest, baselines (`ols_history` is the bar), paired player-cluster and season-level intervals, interval calibration, leakage audit, holdout ledger, pre-registered decision rule, artifacts, data fingerprint | targets `fg3_pct`, `ft_pct` (+ a sampling-variance model for `ts_pct`); candidates `state_space`, `state_space_role`, `beta_binomial`; `PREREGISTRATION_R92` (+5 amendments, §8); `Protocol` now carries its pre-registration and prior ledgers |
| Candidate lifecycle (R9.1) | `train_candidate` is **still the only write path**: protected-state fingerprint, read-only computation guard, isolation assertions, idempotent re-use | a model with a posterior of ability stores it as `inferred` rows beside its forecast (same version, same guarantees) |
| Contract (R9.1) | `PlayerIntelligenceRecord`, `Interval`, `Calibration`, `ModelRef`, `Provenance` | `Reliability`, `conditioning` (required on projections), `Interval.kind` (`prediction` / `credible`), `EvaluationStatus.BENCHMARKED`, `Sample.makes/counts_quality/seasons_used`, `Provenance.reproducibility` |
| Serving | FastAPI v1 conventions, `NotFoundError`/`DomainError` handlers, `Settings` flags | `PlayerIntelligenceService`, `/players/{id}/intelligence` + `/player-intelligence/catalog` (**off by default**; whether the routes appear in the OpenAPI schema is decided when the process starts) |

Not touched: the frontend's data flows, TEI, `domain.skills` / `IntelligenceService` (the legacy percentile skill vector), Cap Center,
Trade Evaluator, Ask Pivot, any active model, any stored estimate. One deliberate, narrow correction was made elsewhere
(Phase 7): the TEI likely-range is now labelled uncalibrated (§9).

## 5. The service

```python
PlayerIntelligenceService(db).get(
    player_id, quantities=None, as_of=None, kinds=("measured",), model_version=None, include_experimental=False,
) -> IntelligenceResponse(records, unavailable, context, notices, requested, as_of)
PlayerIntelligenceService(db).get_many(player_ids, ...)   # same question for a roster; one shared cutoff
PlayerIntelligenceService(db).catalog()                   # what is offered, what is declined, and why
```

* **Quantities** are ids from the registry (`ts_pct`, `fg3_pct`, `ft_pct`, `ast_pct`, `ast_to_ratio`, `reb_pct`, `oreb_pct`, `dreb_pct`,
  `usg_pct`, `minutes_per_game`, `games_played`). Asking for a dimension Pivot cannot see (`defensive_contribution`,
  `overall_skill_rating`, …) returns an `Unavailable` with the reason — it is never an error and never a number.
* **`as_of`** is an information cutoff (a season label; whitespace and look-alike digits are normalised to the canonical label, so `" 2025-26 "` is `2025-26`). Measured rows are filtered to `<= as_of`; stored models are selected by the cutoff
  they were trained at; nothing later is read. Default: the latest ingested season.
* **`kinds`**: `measured` (default), `inferred`, `projected`. Measured needs only data integrity.
* **Measured values state what is known and no more.** Where NBA.com's rounding leaves a season's attempt count undetermined (996 of 5,483 player-seasons carry a range), the record serves the *published* rate
  (exact to its precision), the attempt **range** (`sample.attempts_min/attempts_max`) and a limitation saying so; if zero attempts cannot be ruled out, there is no rate and the reason says "undetermined", never "no attempts".
  Implausible values (minutes per game outside [0, 53], assist-to-turnover outside [0, 60], true shooting above 1.5, negative counts) are integrity failures, not data; a player with no games gets "played no games".
* **Model outputs are read, never computed.** A request never trains or writes. A cutoff with no stored model is reported as
  *not materialised*.
* **Gating (`serving_decision`, one rule, applied everywhere):** validated requires **both** `status = 'active'` **and** `is_active = true` (plus `holdout_confirmed`; nothing qualifies
  in R9.2) — an inconsistent pair (a half-made promotion) is unservable, as is any status string the code does not know; `candidate` → only with `include_experimental=true`, and always labelled (`model.status = "candidate"`, `model.evaluation_status`);
  `rejected`/`retired` → never. An evaluation that `failed` blocks the **projections** of that model, on request or not, and a *stale*
  failure stays a failure (staleness can only lower a status). An **ability estimate** is governed by its own pre-registered serving rule
  (its model's forecasts non-inferior to the baseline, its predictive interval calibrated), so a model whose *forecasts* were not
  confirmed (true shooting) can still serve an ability estimate — labelled, with that fact stated in the record's limitations.
* **The registry's evidence is attached only to the model it describes.** A stored model gets the registry's evaluation status, reference
  and interval calibration only if it is the same method, was evaluated against one of the registry's source experiment runs, was
  trained under the configuration that experiment used (window, minute floors, seed, interval level) on the same data fingerprint, and
  is not stale. Any other stored model — trained on other data, never evaluated, or merely sharing a method name — is shown with its
  *own* stored evaluation (default `unevaluated`), with no calibration, and a limitation saying so.
* **Withheld means nobody.** If the registry withholds an (quantity, kind), no request returns it — naming a `model_version` does not change that.
* **A reliability floor for inferred ability** (`INFERRED_MIN_RELIABILITY = 0.30`): below it the estimate would be mostly the league curve, which
  over-predicts low-volume players (measured, pooled over everyone who played next season: three-point +3.1 / +1.2 / +0.2 points in the reliability bins [0, 0.1) / [0.1, 0.2) / [0.2, 0.3) and free throws +3.2 / +3.5 / +2.0, against within 0.6 points from 0.3 up — `results/selection_check.json`; the floor is a single uniform line, and players selected on *not* playing next season remain over-predicted above it). The measured value is still returned. A player
  with no attempts in any season the model saw gets nothing to infer from, not the league curve.
* **Refusals are data:** `Unavailable(quantity, kind, reason, requirement)`; reasons include *no attempts, so the rate is undefined (it is not
  0%)*, *no statistics for this player in {season}*, *integrity check failed: …*, *not materialised*, *the player is not in the scored population*.
* **Context** (player, the cutoff season's team, age, games, minutes, and the rule-based role descriptor *labelled as not a measure of
  ability*) travels with the answer so a downstream tool can keep it.

## 6. The record contract

`PlayerIntelligenceRecord` (R9.1) with R9.2's additions. The validators, not conventions, enforce:

| Rule | Enforced by |
| --- | --- |
| a measured value has no model and no forecast interval | contract validator |
| an inferred/projected value names its model version and evaluation status | contract validator |
| a projection names the period it forecasts, its information cutoff (which must precede it), **and what it is conditional on** | contract validator |
| only an inferred record carries a `Reliability`; only a projection carries `conditioning` | contract validator |
| a **credible** interval (for latent ability) cannot carry an empirical coverage claim; a **prediction** interval carries its calibration or says it has none | `Interval` validator, `reliability_statement()` |
| rates are fractions of 1; "no attempts" is unavailable, not 0 | `measured.py`, `targets.py` |

Every record carries: canonical `player_id`, `quantity`, `unit`, `period` (season, season type, `as_of_season`), `sample` (games, minutes,
attempts, makes, how the counts were obtained), `model` (name, version, status, evaluation status and reference, methodology, feature
definitions), `provenance` (sources and retrieval time, data snapshot id, code commit, **reproducibility** block: seed, training window,
fitted hyperparameters, training counts), `assumptions`, `limitations`.

## 7. Persistence and versioning

No new table and **no migration**. The R9.1 candidate store is the persistence layer:

| Row | Where | Key |
| --- | --- | --- |
| a model version | `model_versions` (`status = 'candidate'`, `is_active = false`, `model_name = player_forecast_<quantity>`, version `cand-<method>-<quantity>-<hash12>`) | unique `(model_name, version)` |
| a projection | `candidate_estimates`, `output_kind = 'projected'`, `target = <quantity>`, `season` = the cutoff, `target_season` = the following season | unique `(model_version_id, player_id, season, target)` |
| an ability estimate | `candidate_estimates`, `output_kind = 'inferred'`, `target = <quantity>@ability`, `target_season = season`; `exposure` = attempts across **every season the filter used** (the projection row keeps the three-season window) | same |
| how the model fared | `model_versions.validation_metrics` (from the experiment artifacts) and `lineage` (data snapshot, environment, seed, fitted hyperparameters) | — |

Append-only by construction: training adds a new version (its id is a hash of configuration *and* data fingerprint) and never updates or
deletes another row; the isolation checks prove it before every commit. The id also carries an **artifact schema tag** (`ARTIFACT_SCHEMA`, currently `r9.2-3`) in the stored configuration, so a store written by older code never shares an id with what today's code would write.
Re-training the same specification on the same data is idempotent, and refuses (loudly) if the code now produces different numbers under an unchanged id: **every stored column** of the forecast rows and
of the ability rows — estimate, interval, exposure and every key of `inputs` — is compared, separately for the two kinds because they share player ids. A refused reuse does not rewrite the version's evaluation record. (R9.2's first implementation pooled the rows and could not be re-materialised; a later version compared only the estimate and would have "reused" a store holding the defects fixed in review while upgrading its evidence label — `test_pi_review_fixes::TestIdempotence`, `TestReuseComparesEveryColumn`.) Two processes materialising at once are safe: the loser of the creation race hits the unique constraint and reuses the winner's version.
Re-materialising after a data refresh creates a *new* version; older versions remain, so a past cutoff can be re-read exactly as it was served **by naming its version**
(by default the servable version for the cutoff to which the registry's evidence *applies* is preferred, then the newest — so a later, never-evaluated `make train-candidate` run cannot silently become everyone's default answer; its version is on the record; measured records are not versioned — they are recomputed from the stored rows).

## 8. How the validation registry decides what is served

`validation_registry.json` is generated from the experiment artifacts by fixed rules (see the script's docstring and the pre-registration; five dated amendments are recorded in
`PREREGISTRATION_R92` and `results/preregistration.json`):

* **projected** — a candidate is recommended only if it advanced in development *and* was confirmed on the holdout (lowest development MAE
  among those); a holdout that was a re-read caps the status at `development_only`; otherwise the best baseline (`ols_history`) is the
  recommended forecaster and is labelled a **benchmark**, never an improvement.
* **inferred** — experimental only if the ability model's own forecasts are within 2% of the best baseline on development and its predictive
  interval covered 75–85% of development outcomes; status capped at `development_only` (ability is latent); otherwise withheld.

Changing what the service serves therefore means changing a committed JSON that names the experiments behind each decision.

## 9. The one change outside the engine: the TEI band

TEI's `tei_low`/`tei_high` were presented as a 10–90% "likely range". R9.1 measured their out-of-time coverage at 60.8% / 57.2%. The
smallest safe correction: the player-detail API serves `tei_range_calibration` beside the unchanged `tei_range_10_90`; the league reference
states it; the UI calls it a *model range* and says it is not a calibrated 80% interval; the methodology page says the same. The TEI formula
and every existing field are untouched. Regression tests pin the numbers to the R9.1 artifacts and the wording to the UI. The Trade Evaluator draws each player's σ from the same band,
so its simulated spread and P(deal helps) inherit the under-coverage: the evaluation payload now carries a `calibration_note` and the methodology page says so; the deal-level bands are
**not** recalibrated (a recommendation for R9.3).

## 10. Extension points

* **A new dimension** = a `QuantitySpec` + (for inferred/projected) a `TargetSpec` with a sampling model + a `Predictor` — it inherits as-of
  discipline, folds, baselines, the pre-registered rule, the candidate lifecycle and the registry.
* **R9.3** consumes `get` / `get_many` and the `context` block; the record's `period`, `model`, `provenance` and `conditioning` are the
  shared context that must travel with a player between tools (see `R9-3-IMPLEMENTATION-RECOMMENDATION.md`).
* **R10 (archetypes)** should consume the measured/inferred vectors *with their reliabilities*; **R11–R14** need `conditioning` and the
  availability results to avoid mistaking a conditional forecast for total contribution.
